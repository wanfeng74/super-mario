# 附3：卡顿修复（v4 渲染缓存优化）

> 用户反馈"有点卡"。根因：`spriteToCanvas` 的缓存 key 在贴图翻转时是 `'f_' + sprite`——`数组 + 字符串` 触发整张贴图所有行拼接（烘焙后 24×34≈820 字符），每帧每个向右走的敌人都在重复做大字符串拼接 + 哈希查找；且 scale 未纳入 key，同一贴图不同缩放会缓存错乱（标题屏 48px 与游戏内 24px 撞车）。

## 修改（engine.js spriteToCanvas）

- **缓存改挂贴图数组对象属性**（`sprite.__canvasCache[k]`，k = `'n1'/'f1'/'n3'…`）：key 变为短字符串，彻底消除每帧大字符串拼接；
- **scale 纳入 key**：不同缩放各自缓存，杜绝错乱；
- 顺带修复翻转敌人（vx>0 向右走）原来 `'f_'+array` 作为 WeakMap key 的隐患；
- 删除废弃的 `_spriteCanvas` WeakMap。

**性能对比**：修复前每帧每敌人 key 拼接 O(820 字符)+WeakMap 字符串查；修复后 O(3 字符) 对象属性取——理论上每帧渲染开销降至原先的 ~1/100（key 部分）。

# 附5：方块不显示回归修复（v6 blockfix）

> 用户反馈"这回直接不显示方块了 / 我笔上只有问号块正常"。这是 v5 静态层缓存引入的显示回归，已在**浏览器 + Falcon 受限运行时模拟**两端复现并修复。

## 现象与根因

| 环境 | 现象 | 根因 |
|---|---|---|
| 浏览器 | 地面缺失（OCR 误判；像素采样证实主画布地面为橙砖 #9c4a00，实际正常） | 无——浏览器一切正常，纯误判 |
| 词典笔（Falcon） | **只有问号块正常**，地面/砖块/管道全不显示 | 问号块（未用）在动态层每帧绘制；其余方块全部走 v5 新增的静态缓存层 `_tileCache`（1008×266 大离屏 canvas）→ **Falcon 受限运行时创建大离屏 canvas 失败 → `_tileCache=null` → 整个静态层被跳过（原代码无兜底）** |

## 修复内容

1. **静态层降级兜底**（engine.js `renderTiles`）：`_tileCache` 为 null（大离屏 canvas 不可用）时，**直接调用 `_renderStaticTiles(ctx, cam, themeCM)` 逐帧绘制静态层到主画布**——地面/砖块/管道/旗杆走 drawSprite 快路径（小离屏 canvas 或逐像素 fillRect），保证显示正确优先。
2. **ensureCanvas 分级容错**：原 `_canCreateCanvas=false` 全局标志会在**任何一次** canvas 创建失败后毒化后续**所有** canvas（包括 24×24 的敌人/砖块小 canvas）→ 大 canvas 失败会把小 canvas 也拖垮（敌人全部降级 fillRect、性能崩溃）。改为：**只有"环境完全没有 canvas 能力"（document/createElement 不存在）才禁用全局；单次尺寸/内存失败不毒化**。
3. **验证**（haasui-falcon-app 验证矩阵）：
   - 构建：`pnpm -C ui package` 成功，manifest（appid 8001865309000002 / version 2.1.3 / quickjs 20200705）正确，app.js.bin md5 记录；
   - 纯逻辑：node mock canvas 追踪 `_renderStaticTiles`——地面 92 次 24×24 drawImage 全部执行、SPR_GROUND 色板 N/O/p 全命中（opaquePx=576）；
   - Falcon 模拟：浏览器 `?falcon=1` 拦截 ≥512px canvas 创建 → `_tileCache=NULL` → **降级路径生效，主画布地面仍为橙砖（MAIN y250=156,74,0），管道/问号块/敌人/角色全正常，无 JSERR**；
   - 模拟器/真机：无头环境无 Falcon 模拟器/设备，交付包内模拟器由用户在 Windows 端自行试玩确认（见使用说明）。

# 附6：卡顿优化（v7 speed）

> 用户反馈 v6 在词典笔上"卡到爆"。v6 为修复方块显示引入了"降级路径"：大离屏 canvas（1008×266 静态层缓存）创建失败的词典笔，改为**每帧整块重画静态层**——其中地面平铺 92 次 24×24 drawSprite blit（软件渲染下 fillRect 调用量爆炸），是卡顿主因。

## 优化内容（engine.js）

| # | 优化点 | 效果 |
|---|---|---|
| 1 | **地面 4 瓦片宽条贴图 `SPR_GROUND_STRIP`**（96×24，= 4 块原版地面砖横向拼接） | 地面平铺 blit 次数 **92 → ~22/帧**（降到 1/4） |
| 2 | **瓦片级视口裁剪**：地面循环按相机位置只画可见列（`gx0=max(0,⌊(scx-t.x)/24⌋)`、`gx1=min(gw,⌈(scx+984-t.x)/24⌉)`，含 1 瓦片余量） | 屏外瓦片不浪费绘制；配合条贴图每帧约 11 条/行 × 2 行 |
| 3 | **换色 canvas 缓存**：`spriteToCanvas` 支持 object 型 colorMap（缓存 key 含换色序列），`drawSprite` 的 colorMap 分支改为——object（地下/城堡主题换色）**走离屏 canvas 缓存 drawImage 快路径**；仅 function（受伤/无敌闪）保留逐帧 fillRect | 地下/城堡关卡的地面/砖块/管道从**逐瓦片逐像素 fillRect（约 80×576 次）**降为 **drawImage blit** |
